# 0005 — Entity model, identifiers and history

## Context

The spec (§4) describes a shared "entity" concept that events, attachments,
relationships and QR codes can refer to, while warning against a model that
becomes too generic (§16).

## Decision

- **Typed tables per domain plus a thin registry.** Each domain has explicit
  relational tables (`items`, `containers`, `locations`, `tasks`, …). A shared
  `entities` table gives every addressable row a common identity
  (`id`, `household_id`, `entity_type`), so events, attachments, relationships
  and QR codes can point at anything. JSONB only for genuinely variable
  metadata.
- **Primary keys are UUIDv7** — sortable, and safe to expose in URLs and QR
  codes. IDs may be generated by the client, which also keeps offline mode (a
  roadmap item) possible later.
- **Current state + event history.** A state change updates the current row
  and inserts an event in the same database transaction. Events record the
  entity, event type, actor or integration source, `occurred_at`,
  `recorded_at`, a validated payload, and a correlation and idempotency key
  where relevant. No full event sourcing.
- **Retention:** domain events are kept permanently. Device telemetry gets a
  retention window, decided in the devices phase.
- **Deletion:** user-facing records are archived (recoverable); drafts are
  hard-deleted; account deletion hard-deletes the user's data (see 0007).

## Alternatives

- One generic entity table with typed attributes — flexible, but the database
  can no longer enforce structure and queries degrade as domains grow.

## Consequences

- Creating an addressable record means inserting the registry row and the
  domain row together.
- Write endpoints accept idempotency keys from the start.
