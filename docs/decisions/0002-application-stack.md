# 0002 — Application stack

## Context

The spec (§11) recommends React + Vite, Tailwind + shadcn/ui, TanStack Query,
Fastify, PostgreSQL, Drizzle, Zod, Better Auth, BullMQ + Redis when justified,
and WebSockets. Running costs should stay minimal.

## Decision

- **Frontend:** React + TypeScript + Vite SPA, installable as a PWA. TanStack
  Query for server state.
- **UI:** Tailwind CSS with headless, accessible primitives and NEXUS's own
  component set — **not shadcn/ui as the look**. Components are mixed from
  whatever looks best, including components the user brings from previous
  projects. The primitive library is chosen when the first shared component is
  built and recorded in `docs/reference/design-system.md`.
- **Backend:** Fastify + TypeScript (ESM), one modular monolith.
- **Database:** PostgreSQL with **Drizzle ORM**. Migrations are generated by
  Drizzle Kit, reviewed before commit, append-only, and applied by an explicit
  command — never at startup.
- **Validation:** Zod, shared between web and API.
- **Auth:** Better Auth (self-hosted) with email + password and Google sign-in.
  TOTP two-factor is available (see 0007). Passkeys later.
- **Realtime:** WebSockets from the API, in the MVP. Changes are fanned out via
  Postgres `LISTEN/NOTIFY`, so no extra broker is needed.
- **Background jobs:** Postgres-backed (pg-boss). Redis/BullMQ only if a real
  requirement appears.

## Alternatives

- shadcn/ui as the base — rejected as the default look; individual patterns
  may still be borrowed.
- Managed auth (Clerk, Auth0) — adds cost and an external dependency for user
  data.
- Polling instead of realtime — the user wants live updates (e.g. a shared
  shopping list).

## Consequences

- No Redis to run or pay for in the MVP.
- `LISTEN/NOTIFY` fan-out assumes a single API instance or a shared Postgres;
  fine for the expected scale.
